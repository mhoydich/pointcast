## Web Push spike: Morning Crew / Court Call alerts

**Answer.** No — "no-install" and "push" are mutually exclusive on iOS: Safari's Push API only works for a site the user has explicitly added to the Home Screen (Share → Add to Home Screen, `display: standalone`), a rule Apple shipped in 16.4 (Mar 2023) and still enforces in 2026; a plain open tab on iPhone cannot receive push at all, and there's no programmatic install prompt like Android's `beforeinstallprompt` — it's a manual, undiscoverable user step. Android Chrome is the opposite: a regular open tab can call `pushManager.subscribe()` and get notifications with zero install, though Chrome 144/145 (Jan 2026) added rate-limiting and silent auto-revocation for permissions on sites users ignore. Cloudflare Workers can send Web Push (VAPID/RFC 8292 + aes128gcm/RFC 8291) — `nodejs_compat` is already on in this repo's `wrangler.toml`, so the standard `web-push` npm package is usable directly, or a lighter webcrypto-native lib (`@block65/webcrypto-web-push`, `draphy/pushforge`) avoids node-polyfill edge cases. `public/manifest.webmanifest` already qualifies as installable (`standalone`, full icon set), but there is currently **no root-scoped service worker** on pointcast.xyz — only `/sparrow` has one (`public/sparrow/sw.js`, no push handlers in it either) — so push needs new infrastructure from scratch: `/sw.js` at root, a subscribe/unsubscribe endpoint, a D1 table for subscriptions, VAPID keys via `wrangler secret`, and dead-subscription (404/410) cleanup.

**Recommendation.** Skip push for now and ship on the 5-second poll the PRD already specs as the fallback (2026-09-28-field-reports-prd.md line 53: "hears it by push or on its next 5-second poll"). For ~10 users on an open /r/board page, a 5s poll is negligible D1/Worker load and needs zero new infra, while push needs a new root sw.js, D1 subscription table, VAPID secrets, and — critically — an iOS-only "Add to Home Screen" onboarding nudge that most casual visitors will never complete, so it would under-cover the exact iOS users it's meant to alert. Revisit push as its own later PR only if usage shows people close the tab/app and miss reveals; if you do, gate it behind an explicit home-screen-install nudge for iOS rather than assuming Notification.requestPermission() alone will reach those phones.

## Field Duels transport spike: D1 polling vs Durable Object hibernation

**Answer.** Keep D1 move rows plus 1s polling, matching what docs/plans/2026-09-28-field-duels.md already finalized. A duel is about 12 D1 writes and 150 reads across two players polling once per second for 70 seconds; D1 charges 0.001 dollars per million rows read and 1 dollar per million rows written, with 5 million reads and 100 thousand writes free per day, so even 1000 duels a day costs effectively nothing. A Durable Object room would need a brand new DuelRoom class, since PRESENCE only counts heads and DRUM_ROOM is a blind relay that would leak hidden picks; it would also be free at this scale under WebSocket Hibernation billing, and would cut reveal latency from up to one second of poll lag down to tens of milliseconds. That latency edge is small next to the game's own 10 second per exchange shot clock, and D1's INSERT OR IGNORE gives free idempotency against LTE retries that a WebSocket approach would have to hand roll on the same carrier NAT courtside phones that already ruled out WebRTC.

**Recommendation.** Ship the PRD's D1 design as written for the field-duels PR and do not move to a Durable Object. Revisit only if duel volume approaches millions per month, or if courtside playtesting shows 1 second poll lag feels laggy inside the 10 second exchange window, in which case add a lightweight DRUM_ROOM poll-now nudge frame rather than moving state off D1.

## Background Sync spike: skip it for PR 3

**Answer.** No — don't build it. iOS Safari has never implemented the Background Sync API in any version, has no experimental flag, and Apple has given no roadmap signal (an Apple Developer Forum thread asking about it has sat unanswered since 2021, still open in 2024 with no official response); only Chromium browsers — Chrome, Edge, Samsung Internet — support it, so a service worker would help zero iPhone users, likely the majority of people at a US rec park. Even on Android the win is capped: the server rejects any observation older than 15 minutes regardless of when the POST lands, so Background Sync could only ever rescue a report inside that same 15-minute window — exactly the window the current localStorage queue in src/scripts/air-client.ts already covers, via its 1s/3s/9s retries, the `online` listener, and a `drain()` call on every poll tick (5s fast-poll, triggered immediately after a queued tap since `begin()` sets `lastOwnAction` before the POST even resolves). The only real gap Background Sync closes is a phone that backgrounds/locks mid-drop and isn't reopened within 15 minutes — an Android-only, narrow edge case.

**Recommendation.** Decline the service-worker/Background Sync scope for PR 3 and ship no code change: the existing localStorage queue (src/scripts/air-client.ts) already reaches everything Background Sync could reach given the hard 15-minute server freshness ceiling and iOS's total lack of support, while a SW would add real complexity (an IndexedDB mirror since service workers can't read localStorage, plus sync-tag coordination to avoid double-posting against the page's own drain()) for a partial, Android-only payoff. The one lever worth keeping sharp instead: the "Saved on this phone. Sending when you have signal." queued-note copy that nudges reopening inside 15 minutes — that recovers the Android gap too, at zero engineering cost.

## Fence stickers: QR vs NFC for /court?c=CODE

**Answer.** QR wins for a chain-link court fence: an outdoor-laminated QR sticker runs about $0.50 each and reads on any iPhone or Android camera with zero setup, while a fence-suitable NFC tag needs an "on-metal" ferrite-backed SKU (~$2+ each, a small plastic puck, not a flat decal) or it detunes against the metal and stops reading altogether. Background reading is close to a wash, not a clean NFC win: iPhone XS+ opens NDEF URL tags with no app via a tap-through system notification, but Android needs NFC toggled on in Settings and, under Android 15/16's newer tag-permission system, also shows a confirmation popup instead of auto-opening — so neither is truly zero-touch anymore, and QR (native Camera/Lens) has the lower device floor across old/cheap Android phones. Both media can carry a rotating code, but the mechanics differ — NFC can be rewritten in the field in seconds with the free "NFC Tools" app (iOS + Android), while QR needs a reprint and a swap trip — though this repo's build-spec already rotates codes server-side (`air_codes`, HMAC-hashed, `valid_from`/`valid_to`, applied via `wrangler d1 execute`, "no deploy"), so a physical tag/sticker only needs to change on Mike's own cadence, not per-abuse-event, since remote/off-code reports are already zeroed out separately. Posting anything on a public court fence needs permission in most municipalities — the two park codes checked (Gainesville TX, Yorba Linda CA) explicitly bar attaching any sign, bill, or sticker to a park fence or structure without sign-off from Parks & Rec or the city manager — and that permission ask, already logged as an open question in the PRD, is the real blocker here, not the QR/NFC choice.

**Recommendation.** Go QR, not NFC: order a small batch of UV-laminated outdoor vinyl QR stickers (~$0.50/ea, ~5yr rated) mounted on a laminated card zip-tied to the fence rail rather than adhesive stuck to the chain-link itself; keep the printed code long-lived and lean on the already-built D1 rotation + remote/on-site distinction for abuse instead of physically re-tapping tags; and email Parks & Rec in parallel now (small removable card, ask informally) since that approval — not the sticker tech — is the long pole before PR 3 ships anything to the actual fence.
