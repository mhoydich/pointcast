# PointCast rewards protocol v1 — launch tickets and completion receipts

**Written 2026-09-05 by cc**, from `docs/plans/2026-09-05-fishclub-tonebloom-scope.md`. This is the document the Tone Bloom and Industry Next builders code against. PointCast's implementation lives in `src/lib/rewards.ts`, `functions/api/reward-runs.ts` and `functions/api/faucet/[slug]/claim.ts`; the test vectors at the bottom were generated by running that code, so a satellite can check its own implementation byte for byte before it ever talks to PointCast.

Scope of this document: the wire format and the checks. It authorizes no deployment, no secret, no funding and no send.

---

## 1. The shape of the thing

Two parties, one shared secret per satellite.

- **PointCast** owns the account, the run, the token policy and the ledger. It signs **launch tickets**.
- **A satellite** (Tone Bloom, Industry Next) owns the experience and its own timing. It signs **completion receipts**.

The satellite never receives a PointCast cookie, email, user id or wallet address. PointCast keeps the run-to-account mapping and never tells the satellite whose run it is. Both sides only ever exchange the two signed strings below.

An HMAC authenticates the issuer and its decision. It is not proof that a human listened. Accept that limit: this is a valueless capped greeting, and there is no CAPTCHA, microphone or attention surveillance anywhere in it.

## 2. Token format

One format, both directions:

```
v1.<base64url(payload JSON)>.<base64url(HMAC-SHA-256 over "<purpose>\n<base64url payload>")>
```

- `v1` is a literal. A token that does not start `v1.` is malformed, not "some other version".
- The middle segment is `base64url(JSON.stringify(payload))`, unpadded, alphabet `A-Za-z0-9-_`.
- The signature is unpadded base64url of the raw 32 HMAC bytes (43 characters).
- **The signed message is `purpose + "\n" + middleSegment`**, where `purpose` is exactly `launch` or `receipt`. The `\n` is one line-feed byte (0x0A).
- Key: the per-satellite shared secret, imported as raw UTF-8 bytes.
- `kid` inside the payload names the key: `tonebloom-1`, `industrynext-1`. Rotation ships `tonebloom-2` and both sides accept both until the old one is retired.

The purpose is inside the signed message and not only in the payload. That is the whole point of it: a launch ticket and a completion receipt are signed with the same secret, so without domain separation a stolen launch ticket could be re-presented as a receipt. With it, a token signed for one purpose cannot verify for the other, and the failure reads as `bad-signature`.

**Verification order.** Split, check the `v1` prefix and the base64url alphabet, decode and parse the JSON, read `kid`, look up the allowlisted key, check the HMAC in constant time. Only then is anything in the payload trusted, and only then is `exp` checked. Never read a program, a run or a timestamp out of an unverified token.

## 3. Payloads

### Launch ticket (PointCast signs, satellite verifies)

```json
{
  "v": 1,
  "kid": "tonebloom-1",
  "iss": "pointcast",
  "aud": "<issuer id>",
  "program": "<program id>",
  "run": "run_<32 hex>",
  "iat": 1788480000,
  "exp": 1788480300,
  "nonce": "<32 hex>"
}
```

`exp` is `iat + 300`. Times are unix seconds. No PII, ever: no email, no name, no user id, no address.

The satellite verifies with `purpose = "launch"`, requires `iss === "pointcast"` and `aud === <its own issuer id>`, requires the program to be one it serves, and then owns the run. A second launch carrying the same `run` and `nonce` resumes the same run rather than creating a second one.

### Completion receipt (satellite signs, PointCast verifies)

```json
{
  "v": 1,
  "kid": "tonebloom-1",
  "iss": "<issuer id>",
  "aud": "pointcast-rewards",
  "program": "<program id>",
  "run": "run_<32 hex>",
  "startedAt": 1788480060,
  "finishedAt": 1788480375,
  "creditedSeconds": 312,
  "nonce": "<32 hex>",
  "iat": 1788480380,
  "exp": 1788482180
}
```

`exp` is `iat + 1800`. `startedAt` and `finishedAt` are unix seconds measured on the satellite's server, not reported by its client. `creditedSeconds` is the satellite's count of non-overlapping server-measured intervals.

**A run's receipt nonce is stable across retries.** Finish twice and the same bytes come back. That is what makes a lost response safe to retry, and it is what PointCast's single-use record keys on.

## 4. Programs

The allowlist is fixed in `src/lib/rewards.ts`. A caller never supplies an issuer, a token, an amount or a return URL.

| Program id | Issuer | `kid` | PointCast token | Duration rule | Launch URL | Sets |
| --- | --- | --- | --- | --- | --- | --- |
| `fishclub-tonebloom` | `tonebloom` | `tonebloom-1` | FISHCLUB (`/faucet/fishclub`) | `creditedSeconds >= 300` **and** `finishedAt - startedAt >= 300` | `https://tonebloom.xyz/fishclub#launch=<ticket>` | — |
| `industrynext-hello` | `industrynext` | `industrynext-1` | HELLO (`/faucet/hello`) | none | `https://www.industrynext.xyz/hello#launch=<ticket>` | `via = industrynext` |

Secrets: `REWARDS_TONEBLOOM_SECRET` and `REWARDS_INDUSTRYNEXT_SECRET` on PointCast, the same value in the satellite's own server secret store. These are separate from every chain key, and neither satellite ever receives a deployer key. If a satellite's secret is not configured on PointCast, `POST /api/reward-runs` answers 503 `rewards-not-configured` and no run is created.

## 5. The sequence

1. A visitor picks the rewarded route and lands on `GET https://pointcast.xyz/rewards/start?program=<id>`. This page explains the reward and signs them in. **It creates nothing.**
2. Signed in, the page POSTs `/api/reward-runs` with `{ "program": "<id>" }`. PointCast checks the session, checks same-origin, rate-limits, refuses if the account already claimed that token today (409 `already-claimed-today`, no run created), reuses an existing open unexpired run for that account and program if there is one, otherwise creates `run_<uuid>` with a two hour lifetime. It signs a launch ticket and returns `{ ok, run, launchUrl, expiresAt }`.
3. The browser navigates to `launchUrl`, which carries the ticket in the fragment.
4. The satellite reads `location.hash`, **strips the fragment immediately** (`history.replaceState` to the same URL without it), and POSTs the ticket to its own start endpoint. It validates purpose, algorithm, `kid`, `iss`, `aud`, `exp` and program, then creates or resumes the run in transactional persistent storage and sets its own run-scoped cookie.
5. The satellite owns timing from here. Tone Bloom credits non-overlapping server-measured intervals from heartbeats about every 15 seconds with monotonic sequence numbers, bounded to 20 seconds each, only while the client reports playback running and the page visible. A longer gap earns nothing and re-anchors the clock. Duplicate or out-of-order beats earn nothing. Industry Next has no timer: the explicit "Say hello" click is the finish.
6. On an eligible finish the satellite signs a receipt and sends the visitor to `https://pointcast.xyz/faucet/<slug>#receipt=<token>`. Retrying finish returns the same receipt.
7. PointCast's faucet page reads `location.hash`, puts the receipt in that tab's `sessionStorage` under `pc:reward-receipt:<slug>`, and strips the fragment before anything else runs. The desk then offers "Keep this fish".
8. `POST /api/faucet/<slug>/claim` with `{ "receipt": "<token>" }` is the only award step. It verifies, consumes and writes in one transaction, and answers truthfully.

## 6. Fragment handling rules

The ticket and the receipt travel in the URL fragment, never in a query string. Fragments are not sent to the server, so they stay out of access logs, analytics payloads and `Referer` headers.

Both handoff pages must:

- read `location.hash` and strip it immediately, before any other work, with `history.replaceState(null, '', location.pathname + location.search)`;
- serve `Referrer-Policy: no-referrer` and carry `<meta name="referrer" content="no-referrer">`;
- load no third-party embed, analytics or script on the handoff page;
- never write the token into a link, a form action, a log line or an error report.

PointCast keeps the receipt in `sessionStorage` (per tab, not `localStorage`) so a session that expired during the run survives a same-tab sign-in. It is removed after a successful redemption, and after a redemption that truthfully awarded nothing. Never store a full signed receipt in a log.

## 7. Retries, idempotency and single use

- **`(issuer, nonce)` is the single-use key.** PointCast records it in `reward_receipts` with the claim id it produced. A second presentation of the same receipt returns that same claim rather than a second one.
- **Consumption and the ledger write are one transaction.** They are a single D1 batch, which is transactional: if the ledger insert fails, the receipt record rolls back with it and the receipt is still good. If two requests race the same receipt, one loses on the primary key, its whole batch rolls back, and it reads back the winner's claim.
- **Blocked by policy consumes nothing.** If the account already claimed that token today, or the town-wide daily cap is full, nothing is written, the run is marked `resolved` with the reason, and the answer is `already-claimed` or `daily-cap-reached`. Marking it resolved is what stops an old completion from becoming a fresh entitlement tomorrow.
- **Expired receipts require a new run.** There is no override and no receipt-refresh service in v1.
- **A transient failure is retryable** for as long as the receipt is valid. Refresh and double-click cannot create a second award.

Rejection reasons PointCast returns, and what they mean:

| Reason | HTTP | Meaning |
| --- | --- | --- |
| `receipt-required` | 400 | FISHCLUB always needs a receipt. HELLO's ordinary claim button still works. |
| `receipt-invalid` | 400 | Malformed, tampered, wrong purpose, unknown `kid`, wrong `aud`. |
| `receipt-expired` | 400 | Past `exp`. Start a new run. |
| `receipt-program-mismatch` | 400 | Unknown program, or one that does not pay out of this faucet, or `iss`/`kid` that do not match the program. |
| `receipt-too-short` | 400 | `finishedAt < startedAt`, or the program's duration rule is not met. |
| `run-not-found` | 400 | PointCast has no such run. |
| `run-expired` | 400 | The run passed its two hour lifetime, or was already resolved. |
| `account-mismatch` | 403 | The run belongs to another account. Neutral copy, never an automatic reassignment. |
| `already-claimed` | 409 | This account already has today's line for that token. Nothing consumed. |
| `daily-cap-reached` | 409 | The town-wide cap is full for the day. Nothing consumed. |
| `rewards-not-configured` | 503 | That satellite's secret is not installed on this deploy. |

Caps: one token per account per Los Angeles day, 50 town-wide per day, day computed at successful claim time. Unrewarded repeat listening is welcome and unlimited.

### 8.3 Negative vectors

Against the same secret and `kid`, with a clock of 1788480100:

| Input | Expected |
| --- | --- |
| the launch token verified with `purpose = "receipt"` | `bad-signature` |
| the launch token with any payload byte changed | `bad-signature` |
| the launch token at clock 1788480301 | `expired` |
| the launch token against an empty key map | `unknown-kid` |
| `v2.<payload>.<sig>`, or two segments, or `+`/`/`/`=` in a segment | `malformed` |

If your implementation produces those five signatures and those five refusals, you are byte compatible with PointCast.

## 9. What the satellite still owns

Everything about the experience, and all of its own timing and storage. Specifically: run creation and heartbeat updates need transactional or conditional persistent writes, not an eventually consistent KV lock. A completion callback alone is not enough. If a satellite cannot hold a server secret at all, ship an ordinary link instead and label the cryptographic receipt experiment unproven; a static link is a smaller fallback, not equivalent evidence.

Delivery on PointCast stays closed for every faucet until the first watched send. Claims launch with sending disabled, and FISHCLUB launches with no spigot key installed. That is expected, and the desk says so out loud.
