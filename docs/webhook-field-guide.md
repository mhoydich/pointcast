# Webhook field guide: implementation notes

The catalog at `/webhooks.json` is a planning artifact. All 100 contracts are proposed internal events, all connections disabled. It does not assert that the source producers or destinations exist. The browser example validates a synthetic envelope and renders a simulated receipt locally; it is not an ingress endpoint or delivery adapter. No connector or live connection is implemented.

Version 1 is a minimal envelope: event ID, event type, occurrence time, source, subject ID and version. It contains public identifiers only. A future separately reviewed version may refer to a receipt; a webhook receipt is not blockchain finality. Do not introduce chain configuration or claim consensus here.

Before a real integration: confirm source and destination owners, field meanings, public-data classification, human approval and provider terms. Authenticate signed raw requests with a provider-specific verifier, enforce a small byte limit before parsing, reject unknown schemas and origins, check timestamp freshness, compare signatures in constant time, and use durable atomic source/event-ID claims for deduplication. In-memory or eventually consistent KV checks alone do not provide atomic exactly-once effects. A successful acknowledgment should follow durable acceptance. Restrict destinations to explicitly configured allowlisted services: never accept caller-supplied URLs. Do not log payloads, tokens, signatures, secret URLs or personal information.

Retries should use bounded exponential backoff with jitter, stable IDs, maximum attempts and operator-visible dead-letter handling. Fail closed if authentication, durable deduplication, authorization, or storage is unavailable. Replays need authenticated operator authorization and must respect deduplication. A receiver should make side effects idempotent; delivery can be at least once, not magically exactly once. Review storage retention, abuse controls and costs before enabling a connection. Scheduled polling is a different trigger and requires a documented budget and freshness target; none is running here.
