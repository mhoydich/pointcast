# Auth state on D1

Date: 2026-09-02

## Decision

PointCast authentication prefers a dedicated D1 database (`AUTH_DB`) and uses
the existing `USERS` Workers KV namespace only when `AUTH_DB` is unbound. The
drum and analytics traffic can exhaust the account-wide KV write allowance;
login availability must not depend on that unrelated write budget.

No browser contract changes. Kukai still signs through Beacon
`requestSignPayload`, Google still uses the same OAuth redirects, the session
cookie remains `pc_session`, and the wallet/login DOM events are unchanged.

## Storage mapping

| Existing `USERS` key | D1 table | Notes |
| --- | --- | --- |
| `user:{id}` | `users` | Canonical user JSON and creation timestamp |
| `identity:{provider}:{id}` | `identities` | Unique `(provider, id)` mapped to `user_id`; identity JSON retained |
| `session:{token}` | `sessions` | Token primary key, `user_id`, and explicit `expires_at` |
| `oauth-state:google:{state}` | `oauth_states` | JSON payload with explicit `expires_at`; consumed once |
| `auth-nonce:tezos:{nonce}` | `oauth_states` | Five-minute replay marker |
| `project-ticket:{code}` | `oauth_states` | Two-minute one-use project handoff |

MetaMask, Solana, and Apple handlers currently persist nothing. Spotify and
Shopify integration credentials/state live outside `functions/api/auth/**` and
remain on their existing storage path in this change.

D1 has no per-row TTL. Reads reject expired sessions and transient state.
Writes opportunistically delete expired rows from `sessions` and
`oauth_states`. Session lifetime remains 30 days and Google OAuth state remains
10 minutes.

When both bindings exist, new auth writes go only to D1. If a session is not in
D1, the session loader checks the legacy KV key, migrates its user and identity
rows, copies the still-valid session into D1, and continues the request. Legacy
identity mappings also read through so a returning wallet does not get a new
account after its old cookie expires. OAuth state issued immediately before the
cutover can be consumed once from KV.

## Cutover checklist for cc

1. Create the database: `npx wrangler d1 create pointcast-auth`.
2. Replace `REPLACE_ME` in `wrangler.toml` with the returned database id.
3. Apply the schema before the Pages deploy:
   `npx wrangler d1 migrations apply pointcast-auth --remote`.
4. Deploy PointCast with the `AUTH_DB` binding.
5. Verify `/api/auth/session` and a real Kukai browser login, including the
   Beacon signature prompt and a page reload that restores the session.
6. Verify a real Google browser login, redirect back to PointCast, and session
   restoration after reload.
7. Confirm the new rows are present in D1 and that normal D1-bound auth does not
   add `user:`, `identity:`, `session:`, or `oauth-state:google:` writes to KV.

## Rollback

Remove or unbind `AUTH_DB` and redeploy. The storage layer immediately returns
to the existing `USERS` KV key layout. Accounts that existed before cutover
remain available there. D1-only sessions/accounts created after cutover are not
dual-written to KV, so those users must sign in again after rollback unless cc
exports them separately.
