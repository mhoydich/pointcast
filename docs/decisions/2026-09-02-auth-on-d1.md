# Auth state on D1

Date: 2026-09-02

> Superseded in part 2026-09-04 (Astra finding 2): migration `0011` adds
> `sessions.authenticated_at`. Session renewal preserves that original proof
> time, and sensitive passkey registration/removal fails closed unless the
> session comes from a sign-in within the last 15 minutes.

## Decision

PointCast authentication prefers a dedicated D1 database (`AUTH_DB`) and uses
the existing `USERS` Workers KV namespace only when `AUTH_DB` is unbound. The
drum and analytics traffic can exhaust the account-wide KV write allowance;
login availability must not depend on that unrelated write budget.

No browser contract changes. Kukai still signs through Beacon
`requestSignPayload`, Google still uses the same OAuth redirects, the session
cookie remains `pc_session`, and the wallet/login DOM events are unchanged.

## Storage mapping

| Existing `USERS` key | D1 table | Notes |
| --- | --- | --- |
| `user:{id}` | `users` | Canonical user JSON and creation timestamp |
| `identity:{provider}:{id}` | `identities` | Unique `(provider, id)` mapped to `user_id`; identity JSON retained |
| `session:{token}` | `sessions` | Token primary key, `user_id`, and explicit `expires_at` |
| `oauth-state:google:{state}` | `oauth_states` | JSON payload with explicit `expires_at`; consumed once |
| `auth-nonce:tezos:{nonce}` | `oauth_states` | Five-minute replay marker |
| `project-ticket:{code}` | `oauth_states` | Two-minute one-use project handoff |

MetaMask, Solana, and Apple handlers currently persist nothing. Spotify and
Shopify integration credentials/state live outside `functions/api/auth/**` and
remain on their existing storage path in this change.

D1 has no per-row TTL. Reads reject expired sessions and transient state.
Writes opportunistically delete expired rows from `sessions` and
`oauth_states`. Session lifetime remains 30 days and Google OAuth state remains
10 minutes.

When both bindings exist, new auth writes go only to D1. If a session is not in
D1, the session loader checks the legacy KV key, migrates its user and identity
rows, copies the still-valid session into D1, and continues the request. Legacy
identity mappings also read through so a returning wallet does not get a new
account after its old cookie expires. OAuth state issued immediately before the
cutover can be consumed once from KV.

## Rollback

Remove or unbind `AUTH_DB` and redeploy. The storage layer immediately returns
to the existing `USERS` KV key layout. Accounts that existed before cutover
remain available there. D1-only sessions/accounts created after cutover are not
dual-written to KV, so those users must sign in again after rollback unless cc
exports them separately.

## Linked identity expansion: passkeys and email magic links

The auth surface now recommends two browser-memory-independent return paths
before the existing providers:

- `passkey` uses WebAuthn discoverable credentials through pinned
  `@simplewebauthn/server@14.0.0` and `@simplewebauthn/browser@14.0.0`.
  Registration is available only to an existing signed session. Login asks the
  authenticator to discover the account, so no username is entered. Five-minute
  registration and login challenges are single-use `oauth_states` rows.
- `email` sends a hashed, single-use, 15-minute token through the native
  `SEND_EMAIL` Worker binding from `hello@pointcast.xyz`. It creates or links
  the `email:<address>` identity and returns to the validated local `returnTo`.
  Linking requires the callback to retain the same signed session that started
  the flow; a forwarded or cross-browser link signs in the email identity
  independently rather than attaching it to the initiating user's account.
  The raw address and token are never returned by the start endpoint. Email and
  IP limits use `PC_RATES_KV`, with `USERS` only as a rollback fallback.

`migrations/auth/0003_passkeys.sql` adds `passkey_credentials`. Credential
public keys, counters, transports, labels, creation time, and last-use time are
kept in D1. Removing a passkey from `/me` removes both the credential and its
linked `passkey` identity. Passkeys intentionally return a clear 503 when
`AUTH_DB` is absent; cryptographic credential records do not fall back to KV.

### Environment and bindings

- `AUTH_DB`: required for passkey credentials; existing D1-first session and
  identity behavior is unchanged.
- `SEND_EMAIL`: native Email Sending binding declared in `wrangler.toml`.
- `PC_RATES_KV`: preferred email/IP rate-limit store; it is already declared.
- `PASSKEY_ALLOWED_ORIGINS`: optional comma-separated exact origins accepted in
  addition to `https://pointcast.xyz`. Because the RP ID stays
  `pointcast.xyz`, browser-test preview origins must be `https` subdomains of
  `pointcast.xyz`; a `pages.dev` origin cannot create a credential for that RP.

No API token or mail secret belongs in the repo. In the Cloudflare dashboard,
Mike or cc must enable Email Routing and Email Sending for the `pointcast.xyz`
zone, complete the sender-domain DNS setup, and attach the `SEND_EMAIL` binding
to the Pages project. Until that is done, `/api/auth/email/start` returns
`email-sign-in-not-configured` JSON and the page remains usable.

### Real-browser acceptance

1. Sign in with the existing Google or Kukai path, open `/me`, label the current
   device, and choose **Add a passkey to this device**. Confirm Face ID, Touch
   ID, device PIN, or the platform-equivalent user-verification prompt appears.
2. Sign out, clear PointCast cookies and local storage, reload, choose Passkey,
   and confirm the discoverable credential restores the same PointCast user.
   Reload once more and confirm the new HttpOnly session is restored.
3. In `/me`, confirm the credential label and last-used date appear. Remove it,
   sign out, and confirm that credential can no longer sign in.
4. While signed in, submit a real address in **Email me a link** and open the
   message in the same browser. Confirm `/me` shows that email as a linked
   identity. Confirm the response did not expose the address or token and the
   message came from `hello@pointcast.xyz`.
5. Sign out and clear PointCast browser state, request another link for that
   address, and confirm it returns to the initiating local route as the same
   linked account. Reopen the same link and confirm it is rejected as used.
6. Repeat with a
   link older than 15 minutes and confirm it is rejected as expired. Send a
   fourth request for one address inside 15 minutes and confirm HTTP 429.
