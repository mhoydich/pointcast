## Why v2

The live v1 contract seeded `showed-up`, `kennel-club-holder`, `resident`, and
`founding-100` in its `kinds` big map. Its immutable parameter type exposes
`attest`, `revoke`, `set_issuer`, `set_paused`, `set_administrator`, and
`set_metadata`, but no `set_kind`. An administrator can change issuers and
pause issuance; it cannot add `streak-7`, `complete-30`, or any later kind to
that KT1. Sending either milestone kind to v1 would fail with
`UNKNOWN_SEAL_KIND`.

V2 keeps the v1 issuer allowlist, revocation, FA2 views, and `NoTransfer`
policy. It adds:

- `set_kind(kind: bytes, enabled: bool, metadata: map)` for administrator-only
  kind registration and retirement;
- `attest_batch(list)` so the issuer Worker can submit milestone attestations
  in one contract call;
- `evidence_uri: option(bytes)` alongside the bounded inline evidence bytes;
- eight genesis kinds: `showed-up`, `kennel-club-holder`, `resident`,
  `founding-100`, `streak-7`, `complete-30`, `post-office-alias`, and
  `x402-receipt`.

The checked-in compile storage is paused, administered by Mike's Kukai
`tz2FjJhB1gb9Xc2qNB7QgFkdBZkGCCRMxdFw`, and seeds Mike, the cc wallet
`tz1PTUzbDzkddTh2uXMuxrGtRL6ty8aoeysY`, and the claim wallet
`tz1UvNjifVKhP6Hm3ytVfWtmTiCxKozcYsSG` as issuers. The origination script
fails closed unless its compiled storage still has those properties and keeps
the existing explicit mainnet acknowledgement plus env-only signer gate.

## Worker dual-contract path

`pointcast-kennel-seals` always treats contract routing as configuration, not
as proof that an operation happened:

- until frozen, `showed-up` remains on live v1;
- when `SEAL_CONTRACT_V2` is a valid KT1, the first deterministic seven-day
  consecutive run earns `streak-7` on v2 and all 30 unique sittings earn
  `complete-30` on v2;
- `SEAL_V1_FROZEN=1` routes pending and future `showed-up` receipts to v2,
  leaving already-attested v1 receipts in place;
- v1 uses a Taquito manager batch of its single `attest` entrypoint; v2 uses
  one call to the contract's `attest_batch` entrypoint;
- D1 compare-and-set receipt states, the signer lock, and the append-only
  operation row form the idempotency boundary. An injected receipt is
  reconciled and is not resubmitted unless the prior hash is definitively
  failed.

`GET /status` reports both contract addresses, enabled/frozen state, routed
kinds, binding readiness, dry-run state, and receipt totals. It never returns
the issuer secret.

## Cutover

Every step is separately verified. A prepared artifact, wallet prompt, or
broadcast is not an originated or applied contract.

1. Review the source and SmartPy 0.24.1 scenario output, then originate v2
   **paused** with `scripts/seal-v2-originate.mjs`. This PR does not execute it.
2. Verify the origination operation, KT1 code, paused storage, administrator,
   eight kinds, and three seeded issuers on TzKT.
3. From Mike's administrator wallet, call `set_issuer` for the actual Worker
   signer with `allowed=true` even when it is one of the genesis issuers; this
   makes the selected operational signer an explicit, freshly verified
   cutover fact.
4. Call `set_paused(false)` on v2 and verify the applied operation and storage.
5. Set the deployed Worker's `SEAL_CONTRACT_V2` to the verified v2 KT1. Keep
   `SEAL_V1_FROZEN=0`, run a read-only dry run, then observe and verify one real
   milestone batch plus its D1 receipt transition.
6. Only after v2 is proven, set `SEAL_V1_FROZEN=1`. Verify `/status` reports v1
   frozen and v2 enabled, then prove the next `showed-up` receipt was attested
   on v2. Existing v1 seals remain readable forever.

Rollback before step 6 is removing `SEAL_CONTRACT_V2` or pausing v2. After
step 6, restoring `SEAL_V1_FROZEN=0` routes pending and future `showed-up`
receipts back to v1; it does not undo either contract's existing attestations.

## Register and `/me` display rule

The contract register keeps v1 and v2 as separate immutable sources. Readers
query both `seals` big maps for every linked wallet, attach the originating
contract address and token id to each receipt, and merge the display by decoded
`kind` rather than by contract.

For each kind, the UI shows one seal group with the number of attestations and
all receipt links available on expansion. The group is active when at least one
attestation across either contract is not revoked; a revoked record on one
contract does not hide an active record on the other. When one representative
receipt is needed, prefer an active v2 record, then an active v1 record, then a
revoked record. Never compare token ids across contracts or imply that a v2
token replaced, transferred, or mutated a v1 token.
