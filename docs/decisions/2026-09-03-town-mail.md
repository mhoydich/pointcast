# Decision: two mail rails for Fable and the PointCast town

**Date:** 2026-09-03

**Status:** implementation ready for review; no mailbox purchased, DNS changed, secret set, migration applied, Worker deployed, or Pages deployment made

## Decision

PointCast uses two deliberately separate mail rails:

1. `fable@pointcast.xyz` is a real IMAP/SMTP mailbox for the cc agent. The local scripts read its credentials only from `~/.config/pointcast/fable-mail.env`, and successful sends append a local receipt to `~/.config/pointcast/fable-mail.log`. Mike's `~/pigeon` client is the intended long-term home; this change does not integrate with Pigeon.
2. Town/application mail uses one `sendMail` adapter. It prefers the Resend REST API when `RESEND_API_KEY` is present, falls back to the existing Cloudflare `SEND_EMAIL` binding, and otherwise reports `{configured:false}`. Collect confirmation, email magic links, and `pointcast-kennel-daily` retain their existing copy and sender addresses.

Resend receiving is isolated at `inbound.pointcast.xyz`. The signed `email.received` webhook is metadata-only, so `/api/mail/inbound` verifies the raw Svix payload, retrieves the full text through Resend's Receiving API, and then writes D1. `svix-id` and Resend email id are unique, making retries idempotent. A newly stored message emits one generic `mail` burst; the burst contains no sender, recipient, subject, or body.

`GET /api/mail/inbox` returns `{from,to,subject,text,receivedAt}` only to a signed-in user with the existing `broadcaster` role, PointCast's current director gate.

1. Buy a mailbox for exactly `fable@pointcast.xyz` from Namecheap Private Email or Fastmail. Before changing any apex MX setting, record the existing `hello@`, `kennel@`, and `wallet@` Gmail forwards and recreate them as provider aliases/forwarders. Namecheap documents that its free Email Forwarding cannot coexist with Private Email or another mail service, so those aliases must be proven at the chosen provider before the MX switch: [Namecheap email forwarding](https://www.namecheap.com/support/knowledgebase/article.aspx/308/2214/how-to-set-up-free-email-forwarding/).
2. In Resend, create the PointCast account, add `pointcast.xyz` as the sending domain, and enable receiving on the separate `inbound.pointcast.xyz` domain. Create an API key with sending and receiving access.
3. In Namecheap **Domain List → pointcast.xyz → Manage → Advanced DNS**, add the exact records Resend displays:
   - SPF: never add a second `v=spf1` TXT record at the same host. If Resend requests SPF at `@`, edit the existing efwd record into one value by inserting Resend's displayed include/mechanism before the existing terminal `~all` or `-all`; for example, `v=spf1 include:spf.efwd.registrar-servers.com include:<resend-value> ~all`. If Resend assigns SPF to a return-path host such as `send`, add its TXT there and leave the apex efwd SPF unchanged.
   - Sending return path: add the MX record and priority Resend shows for its return-path host (commonly a `send` host). This is not the apex inbound MX.
   - DKIM: copy every selector and target exactly. For each CNAME shown by Resend, choose **CNAME Record**, put only the relative selector in Namecheap's **Host** field, and put the full Resend target in **Value**. If the Resend dashboard shows a DKIM TXT rather than a CNAME, use the record type it shows. Do not invent selector values.
   - Inbound: add Resend's receiving MX at Namecheap host `inbound`, with the exact target and priority Resend shows. Do not add Resend receiving MX records at `@`; keeping receiving on the subdomain avoids replacing the apex mailbox/forwarding route. Resend recommends this separation when a domain already has mail service: [custom receiving domains](https://resend.com/docs/dashboard/receiving/custom-domains).
4. Wait for Resend to show sending and receiving as verified. Send a delivery test from both `hello@pointcast.xyz` and `kennel@pointcast.xyz`, then test an inbound message to an address at `inbound.pointcast.xyz`. Verify the recreated apex `hello@`, `kennel@`, and `wallet@` forwards still arrive in Gmail.
5. In Resend **Webhooks**, add `https://pointcast.xyz/api/mail/inbound`, subscribe only to `email.received`, and copy the endpoint's signing secret for the cc secret-setting step. Resend requires verification against the raw request body: [webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests).

   ```sh
   chmod 700 ~/.config/pointcast
   $EDITOR ~/.config/pointcast/fable-mail.env
   chmod 600 ~/.config/pointcast/fable-mail.env
   ```

   The file has exactly these names; the scripts use the same mailbox username/password for SMTP authentication:

   ```dotenv
   IMAP_HOST=<provider IMAP host>
   IMAP_PORT=<provider IMAP TLS port>
   IMAP_USER=fable@pointcast.xyz
   IMAP_PASS=<mailbox password or app password>
   SMTP_HOST=<provider SMTP host>
   ```

## DNS boundary

DNS is managed at Namecheap, not Cloudflare. Cloudflare hosts the Pages/Workers compute and secrets only. Resend's inbound MX belongs exclusively on `inbound.pointcast.xyz`; it must not replace the chosen apex mailbox provider's MX records.
