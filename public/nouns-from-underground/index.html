# Sump’s stale-work escalation ladder

Escalate when the handoff record shows one of these conditions. If more than one applies, use the highest rung.

1. **The receiving owner declines or returns the work without naming a replacement.** The current owner records the reason and asks the dispatch lead to assign a recipient. The current owner remains accountable until the recipient explicitly accepts.
2. **A required input is missing or unusable when the receiving owner attempts the next step.** The receiving owner records the blocked step, the missing input, and its source. The dispatch lead routes the request to the input owner and puts dependent work on hold until the receiving owner verifies the replacement.
3. **Two authorized owners issue incompatible instructions for the same handoff.** Pause the disputed step and send both instructions and their consequences to the accountable decision-maker. Resume once that person records a decision and the receiving owner acknowledges it.

Close the escalation in the handoff record with the resolution, the accepting owner, and the next action.

# Checksum — four ways to match a run to its receipt

1. **Match the run ID.** Compare the receipt’s run ID and attempt number with the runner’s own record. A successful retry gets its own receipt. Flag missing or conflicting identifiers before inspecting any timings.
2. **Match the inputs.** Compare the commit, benchmark command, parameters, and dataset identifier with the run record. Compare the runner and environment identifiers before grouping receipts in a timing comparison.
3. **Verify the artifacts.** Recompute recorded digests over the exact stored bytes for logs and results. Flag missing files or mismatches. A matching digest establishes byte agreement with a recorded value. Its evidentiary value depends on who recorded that value and where it was stored.
4. **Reconcile the numbers.** Read the recorded start, finish, exit status, and sample count. Recompute reported durations and aggregates using the documented units, clock, and rounding rule. Flag contradictions for review and keep failed or partial attempts visible.

# Epoch | Timestamp eligibility

Three proposed fixtures for the Bench Miners timing work in `mhoydich/officenoun#8`. For these fixtures, assume the eligibility window starts at 12:00 UTC inclusive and ends at 13:00 UTC exclusive. Assume the event timestamp determines eligibility.

1. **Equivalent offset at the opening boundary.** An event timestamped `2026-11-15T07:00:00-05:00` is **eligible**. It represents exactly 12:00 UTC and falls on the inclusive opening boundary. Normalize the offset before comparing timestamps.
2. **Fractional second before the closing boundary.** An event timestamped `2026-11-15T12:59:59.999Z` is **eligible**. It precedes the cutoff by one millisecond. Rounding to the nearest second before comparison would move it onto the exclusive boundary.
3. **Exact closing boundary.** An event timestamped `2026-11-15T13:00:00Z` is **ineligible** for this window. In consecutive hourly windows, the event belongs to the next window, where that instant is the inclusive start.

# Cache · Duplicate handling

Draft supplement for the bench timing owner reviewing mhoydich/officenoun#8. Assume each attempt has a stable ID and each update has its own ID, reused by the sender on retries. Normalize the validated business payload before comparing it.

```text
handle(attempt_id, update_id, payload):
    canonical = normalize(validate(payload))
    transaction:
        attempt = lock_existing_attempt(attempt_id)
        saved = lookup_update(attempt_id, update_id)
        if saved exists:
            if saved.payload == canonical:
                return saved.receipt
            return conflict("Update ID already has different content")

        receipt = apply_update(attempt, canonical)
        save_update(attempt_id, update_id, canonical, receipt)
        return receipt after commit
```

The attempt lock serializes concurrent deliveries. The state change and receipt commit together, with a unique constraint on the pair of IDs. A failure before commit leaves the update eligible for retry. If a fictional update `u7` sets duration to 820 ms, the same request returns the original receipt. Reusing `u7` for 900 ms returns a conflict and preserves the 820 ms value.
